USER'S E2EE OBJECTIVE
Build real E2EE such that journal data is encrypted in the browser before requests reach the backend, MongoDB stores ciphertext, and decryption happens in the browser. The server handles authentication, authorization, storage, and delivery, and never receives plaintext journal content or plaintext encryption keys. Users should use journals across devices and have recovery capability if they forget their encryption passphrase.

SECURITY MODEL AND LIMITATIONS TO DOCUMENT
- Intended protection: backend operators, database operators, and database backups should not be able to read encrypted journal fields without user-held unlock/recovery secrets.
- The server still learns account/authentication data, ciphertext sizes/timing, record ownership, and the entry date (date is explicitly allowed to remain plaintext). Other metadata should be encrypted per user's decision below.
- E2EE does not protect plaintext while the user is actively viewing/editing it in a compromised device/browser.
- XSS or malicious same-origin JavaScript can potentially access plaintext and an unlocked CryptoKey. A malicious or compromised app update delivered to the browser can subvert the client-side crypto.
- Browser extensions, malware, screenshots, clipboard, compromised devices, service operators, and availability/data deletion attacks remain outside E2EE protection.
- Recovery is conditional: if both encryption passphrase and Recovery Key are lost, the backend cannot recover the Master Key or plaintext. A Chronicle login-password reset must not reset E2EE keys.
- Avoid claiming perfect memory erasure for JS buffers; overwriting temporary typed arrays is best effort only.

USER DECISIONS ALREADY GIVEN (TREAT AS REQUIREMENTS)
1. Encrypt all journal fields except date. That means title, content, mood, tags, and other entry payload fields should be included in ciphertext. Date remains plaintext by explicit choice.
2. Apply encryption to all entries, not merely new entries. Existing plaintext entries are in scope for a later browser-side migration after unlock; do not execute migration in the initial implementation. Preserve originals until encrypted copies are verified; migration must tolerate interruption and avoid duplicate/destructive work.
3. Leave image encryption out of scope for now. Existing Cloudinary images remain unencrypted; this is a known limitation to disclose. Encrypting the entry content may conceal image URLs in the database but does not encrypt image bytes hosted by Cloudinary.
4. Disable drafts for now. The existing local draft behavior stores plaintext in localStorage; encrypted mode must not silently continue that behavior. This is a deliberate functionality tradeoff pending future design.
5. Use AES-GCM for all encryption, including journal payloads and key wrapping. Do not silently switch key wrapping to AES-KW. Any exact Web Crypto API design must be checked for support and handled correctly.

IMPORTANT: These are user-level constraints. The complete architecture (including KDF, payload envelope, APIs, schemas, migration and tests) has NOT yet been proposed or approved. In particular, "GCM for all" means the architecture should use AES-GCM for wrapping too; explain fresh random IVs and why wrapped Master Key copies need independent IVs.

PROPOSED CRYPTOGRAPHIC MODEL TO EVALUATE IN PHASE 1 (NOT YET APPROVED)
Key hierarchy:
- Random 256-bit Master Key (MK) encrypts journal payloads using AES-256-GCM.
- Separate user-created encryption passphrase is never sent to server and is distinct from Chronicle login password.
- Derive a KEK from passphrase, random 16-byte salt, and KDF parameters. The KEK only encrypts/wraps MK.
- A random Recovery Key independently protects a second copy of MK. Show it once, require confirmation, and explain safe offline storage. Never store it plaintext server-side.
- Backend stores KDF identifier/parameters, salt, wrapped MK and GCM IV; recovery-wrapped MK and its independent GCM IV; algorithm/version metadata. No passphrase, raw MK, Recovery Key, or KEK on backend.
- Each GCM encryption operation under any particular AES key MUST have a unique fresh random 12-byte IV. Salt is for KDF and must not be confused with IV. AES key size 256 bits.
- Consider AES-GCM AAD to bind ciphertext to stable context such as owner ID, entry ID, schema/version and field purpose, preventing ciphertext substitution across records/contexts. Decide exact canonical encoding and migration rules. Avoid AAD fields that change during normal editing unless planned.
- Web Crypto wrapKey('raw', masterKey, kek, {name:'AES-GCM',iv}) requires the wrapped key be extractable. Proposed lifecycle: generate transient extractable MK only for setup/wrapping; create both independently wrapped copies; then import/use a non-extractable working CryptoKey limited to encrypt/decrypt. Verify exact browser support/API semantics. Use separate keys/IVs for passphrase and recovery wraps.
- For recovery, unwrap with Recovery Key, create a new salt and KEK from a new passphrase, rewrap same MK with fresh IV, verify unwrap/decrypt, then update only passphrase-wrap metadata. Recovery wrap remains unchanged. For Recovery Key rotation, unlock MK, create and confirm new key, rewrap MK with fresh IV, verify, and atomically update recovery metadata.
- Passphrase change rewraps same MK; journal data does not need bulk re-encryption.
- No device-specific key is needed for the simple multi-device goal: each device authenticates, downloads public encryption metadata, and derives/unlocks from same passphrase. Keep MK only in memory as a non-extractable CryptoKey after unlock; logout/expiry locks and discards references. Refresh requires unlock again. Define cross-tab lock behavior using messages/events without storing key material.

KDF CHOICE STILL OPEN:
- Must critically compare native Web Crypto PBKDF2-SHA-256 to audited browser Argon2id implementation.
- PBKDF2 has native broad Web Crypto compatibility and low dependency complexity, but is compute-hard rather than memory-hard.
- Argon2id is memory-hard, but needs browser/WASM dependency, compatibility/performance analysis and supply-chain review.
- Do not choose a count/parameter arbitrarily. Benchmark on target device classes and select documented parameters that produce a reasonable user unlock delay while resisting offline guessing. Exact recommendation and benchmark plan belong to Phase 1; any benchmark implementation/run needs authorization if it changes files or installs dependencies.

JOURNAL ENVELOPE / METADATA DIRECTION TO EVALUATE:
- Encrypt one canonical UTF-8 JSON payload containing title, content, mood, tags, and any additional sensitive per-entry fields. Keep date outside ciphertext as required. One payload reduces leakage between fields and simplifies authenticated encryption/versioning.
- Store opaque ciphertext, fresh GCM IV, encryption/schema version, plaintext date, owner/user reference, and standard DB timestamps/ID. Decide whether createdAt/updatedAt remain visible (likely operational metadata leakage) and document it.
- Backend treats ciphertext as opaque and does not decrypt or inspect encrypted fields. Validate strict types, byte/encoded sizes, exact IV length, supported algorithm/version and date; do not permit unbounded payloads.
- Since date remains plaintext, server may sort/filter on date and paginate unfiltered date pages. Encrypted content/title/mood/tags require browser-side filtering/search/stats after decryption. To correctly paginate search results, client may need all entries or a separately approved strategy; explain scaling impacts.

USER FLOWS REQUIRED IN ARCHITECTURE PROPOSAL:
1. Initial setup: user opts in; create passphrase; random salt; derive KEK; generate MK; make passphrase-wrapped copy; generate recovery secret and independently wrap MK; show recovery key; require user confirmation; test that recovery material can unwrap; persist metadata only after both wrapping paths and confirmation work. Design failure-safe ordering to avoid a half-enabled unrecoverable account.
2. Login/unlock: existing Chronicle login remains; fetch crypto metadata; user enters separate passphrase; derive KEK; unwrap MK; on error show generic unlock failure; keep working non-extractable key in memory. Logged-in-but-locked UI must not send/render plaintext journal content.
3. CRUD: encrypt fields in browser before API create/update; retrieve ciphertext; decrypt in browser; handle tampered/corrupt ciphertext safely without silently overwriting; lock state prevents CRUD.
4. Passphrase change: unlock existing MK, derive new KEK with fresh salt, wrap same MK with fresh IV, verify and update metadata. Existing recovery wrap stays valid. Explain network failure/concurrent-update behavior.
5. Recovery: login, request recovery-wrapped MK, input saved Recovery Key, unwrap, choose new passphrase, derive fresh KEK/salt, create verified new passphrase-wrap; keep recovery wrap valid.
6. Recovery-key rotation: unlock, generate new random recovery key, create/verify new wrapped copy, user confirms saved key, then update server metadata; old recovery key invalidated only after successful update.
7. Multi-device: same account, retrieve same metadata, enter passphrase, derive same KEK, unlock same MK. No server decryption.
8. Logout/token expiration/refresh/tabs: no localStorage/sessionStorage persistence for MK, KEK, passphrase or Recovery Key. Define in-memory lock lifecycle and cross-tab signaling.
9. Legacy migration: separately approved future work; browser unlocks, fetches original plaintext entry, encrypts complete payload, verifies by decrypting locally, writes ciphertext with concurrency/idempotency marker, confirms encrypted record before preserving/deleting old copy. Do not destructively remove plaintext without explicit user approval. Handle interrupted/repeated runs and mixed old/new entries clearly.
